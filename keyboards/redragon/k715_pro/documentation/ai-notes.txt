FR5082DM SPI PROTOCOL (register 0x51)
---------------------------------------
  SPI read of register 0x51 returns 12 bytes (BLE connection status):
    Byte  0  : 0x01  (status type / header byte)
    Byte  1  : Connection state:
                 0x00 = disconnected
                 0x01 = discovering / pairing
                 0x02 = connected
                 0x03 = connected (with updated channel state?)
    Byte  2  : BT channel (0-2 for channels 1-3, masked & 0x7F for comparison)
    Bytes 3-4: Unknown (0x00)
    Byte  5  : 0xFF
    Bytes 6-10: 0x00
    Byte  11 : 0xFF

  Polling behavior: STM32 polls register 0x51 up to 9 times with 10ms delay,
  checking byte 2 (connection state) until it matches expected value.
  SPI read function: 0x080038DC (core SPI transfer)
  BLE poll function: ~0x08003A8C (uses 0x080038DC, retries 9×)

BLE STATE MACHINE DETAIL (from live debug logs)
================================================================================

FR5082DM Register 0x51 Response Format (12 bytes):
  Byte 0: Message type
            0x01 = status report
            0x03 = confirmed / updated connected state (seen after initial connect)
  Byte 1: Connection state
            0x00 = disconnected
            0x01 = discovering (BLE advertisement scan, pairing mode)
            0x02 = connected
  Byte 2: BT channel (0x00 = not applicable / channel 1 in some contexts)
  Bytes 3-4: 0x00 (unknown)
  Byte 5:  0xFF (padding/unused)
  Bytes 6-10: 0x00 (unknown)
  Byte 11: 0xFF (padding/unused)

BLE Connection State Machine:
  PAIR sequence (FN+channel):
    1. "set bt_chn:N" → "send pair..."
    2. Poll 0x51: byte[1]=0x00 → "mark bt disconnected" → "bt pair again"
    3. Send pair again → poll 0x51: byte[1]=0x01 → "bt discover:0x01,chn:N,p:1"
    4. Poll 0x51: byte[1]=0x02 → "bt connected:0x01,chn:N" (initial)
    5. Internal: "update connected:0x03,chn:N,b:0x01"
    6. Poll 0x51: byte[0]=0x03,byte[1]=0x02 → "bt connected:0x03,chn:N" (confirmed)
    Timeout after ~60s: "bt pair/reconn timeout!"

  RECONNECT sequence (quick tap FN+channel):
    1. "set bt_chn:N" → "send reconn..."
    2. Poll 0x51: byte[1]=0x02 → "bt connected:0x01,chn:N" (fast path if already known)
    3. Or: byte[1]=0x00 → "bt reconn again" → retry

LED BLINK API (led_blink_start):
  Signature: led_blink_start(timestamp):led GROUP, LED_ID, (on_ms,off_ms), count, flags
  Groups:
    0 = Bluetooth / indicator LEDs
    2 = Keyboard indicator LEDs

  LED_ID reference (Group 0 = BT indicators):
    1 = BT channel 1 indicator
    2 = BT channel 2 indicator
    4 = BT channel 3 indicator  (gap — LED 3 may be USB or WIN/MAC indicator)

  LED_ID reference (Group 2 = keyboard):
    11 = encoder ring indicator (mode change blink)
    12 = RGB speed/mode indicator

  Flags: 0 = normal, 88 (0x58) = BT pairing/reconnect indicator (long sequence)

  Examples:
    Pairing BT3:       led 0, 4, (250,250), 120, 88   -- blinks 120× while pairing
    Reconnecting BT1:  led 0, 1, (500,500), 60, 88    -- blinks 60× while reconnecting
    Encoder mode chg:  led 2, 11, (300,300), 2, 0     -- 2 blinks to confirm mode
    Speed adjust:      led 2, 12, (250,250), 3, 0     -- 3 blinks to confirm

FR5082DM CHIP DETAILS (from Freqchip datasheet v1.3.4)
================================================================================

MANUFACTURER: Freqchip (www.freqchip.com) — NOT Phytec/Fangtek (previous assumption incorrect)
PACKAGE: QFN40, 6×4mm

ARCHITECTURE:
  - Dual-core: 32-bit Cortex-M3 @ 48MHz (BT/app subsystem)
  - Floating-point DSP @ 156MHz (audio & algorithms)
  - 96KB + 416KB = 512KB SRAM total
  - 1MB XIP Flash for Cortex-M3 (BT firmware)
  - Bluetooth 5.0 Dual Mode (BR/EDR + BLE)

PHYSICAL INTERFACES (relevant to keyboard use):
  - UART: for AT commands AND debug output
      → STM32 PC11 = UART4_RX ← FR5082 UART_TX (confirmed in board_init)
      → STM32 PC10 = UART4_TX → FR5082 UART_RX (inferred, not yet confirmed in code)
      → The "send pair..." / "send reconn..." commands are likely AT commands over UART
      → "spi rd 0x51" status checks are separate reads over SPI2
  - SPI/QSPI: up to 104×4 Mbps QSPI; used here in standard 1-bit SPI mode
      → STM32 SPI2 (B12/B13/B14/B15) ↔ FR5082 SPI pins
  - I2C: for external EEPROM or devices
  - USB-OTG: present on chip (not used in keyboard application)

POWER SUBSYSTEM (critical for battery design):
  - VBAT input: 2.5V – 4.3V (direct LiPo battery connection)
  - VCHG input: 4.5V – 5.5V (USB charge input)
  - Built-in charger circuit (VCHG pin = charger state detection)
  - Dual on-chip DC/DC converters (system @ 1.4V, audio @ 1.8V)
  - On-chip LDO for VDDIO (1.8–3.3V, typ 2.9V output, 120mA max)
  - Sleep standby: <70µA @ 500ms sniff interval
  - Power off: <3µA leakage
  ⚠️  The FR5082 manages battery charging autonomously — STM32 only reads charge state

BLE PROFILES SUPPORTED:
  - A2DP v1.3, AVRCP v1.6 (audio streaming/control)
  - HFP v1.8 (hands-free)
  - SPP v1.2 (serial port — likely used for STM32↔FR5082 command channel)
  - HID profile NOT listed in datasheet — custom Freqchip firmware in ROM
  - "Human Interface Devices" listed as typical application

DUAL-CHANNEL STM32 ↔ FR5082 COMMUNICATION ARCHITECTURE:
  Channel 1 — UART (command/response):
    STM32 → FR5082 (UART4_TX, PC10): sends AT-style commands
      "send pair..."    = AT command to start BLE pairing on channel N
      "send reconn..."  = AT command to reconnect to known device on channel N
    FR5082 → STM32 (UART4_RX, PC11): sends status/debug responses
  
  Channel 2 — SPI2 (status polling):
    STM32 polls FR5082 register 0x51 (12 bytes) to read connection state
    Used to verify commands completed, detect connect/disconnect events

FR5082DM GPIO PINS (QFN40, relevant outputs):
  PC0-PC5, PC6-PC7: Multi-Function GPIO
  PB0-PB7:          Multi-Function GPIO
  PA0-PA3:          Multi-Function GPIO (DM variant only; DS has PA0 only)
  PD6-PD7:          Multi-Function GPIO (DM variant only)
  Total: 22 GPIOs (DM), 18 GPIOs (DS)
  ⚠️  FR5082 GPIO port names (PCx, PBx, PAx) are unrelated to STM32 GPIO names

FR5082 SPI PROTOCOL — COMPLETE SPECIFICATION (from btspi.c/h + k715_pro.h)
================================================================================

SPI CONFIGURATION:
  Mode 3 (CPOL=1, CPHA=1)
  Clock divisor: 32 → 72MHz / 32 = 2.25 MHz
  CS: B12 (active low, with 200µs setup delay after assert)

SPI FRAME FORMAT:
  Single packet TX (STM32 → FR5082):
    [0x5A] [len+1] [cmd] [data...] [checksum]
    checksum = sum of bytes[1..N-1]
    max payload: 12 bytes (MAX_SPI_BLE_SINGLE_PACKET_LENGTH)

  Single packet RX (FR5082 → STM32):
    [0x5A] [len+1] [cmd|flag] [data...] [checksum]
    bit 7 of byte 2: 0=single, 1=multi-packet
    Total frame: 16 bytes (MAX_BLE_SPI_RX_FRAME_MAX_SIZE)

  Multi-packet TX:
    [0x5A] [13] [cmd|0x80] [seq|end_flag] [data×11] [checksum]
    end_flag (bit7 of seq byte): 1=last packet, 0=more packets
    max 11 payload bytes per packet (MAX_SPI_BLE_MUL_PACKET_LENGTH)

  INTERRUPT PIN: B9 (EXT_READ_SPI_SLAVE_INT_PIN)
    FR5082 asserts B9 low (falling edge) to notify STM32 that data is ready
    Configured as INPUT_PULLUP, falling-edge interrupt

spi_slave_dev_info_t STRUCTURE (12 bytes, packed):
  Bytes 0-3 (uint32 bitfield, little-endian):
    bit  0:    NumLock state (1=on)
    bit  1:    CapsLock state (1=on) — explains 0x01↔0x03 alternation in logs!
    bit  2:    ScrollLock state (1=on)
    bit  3:    reserved
    bit  4:    remote_btn_down
    bit  5:    remote_btn_dec
    bit  6:    remote_btn_add
    bit  7:    remote_chg
    bits 8-15: state_bt (BT connection state: 0=disconn, 1=discover, 2=connected)
    bits 16-23: state_24g (2.4GHz state — unused in this keyboard)
    bits 24-31: state_usb (USB state)
  Byte 4:  mode (device mode: 0=BT, 2=USB, 8=poweroff)
  Byte 5:  eff_mode (RGB effect mode, 0xFF=unset/default)
  Byte 6:  eff_bright (RGB brightness)
  Byte 7:  eff_speed (RGB speed)
  Byte 8:  eff_r (RGB red)
  Byte 9:  eff_g (RGB green)
  Byte 10: eff_b (RGB blue)
  Byte 11: ch (BT channel, 0xFF=unset)

  ⚠️  EARLIER ANALYSIS CORRECTION: bytes 0 (0x01/0x03) in debug logs are NOT a
      "message type" — they are the NumLock/CapsLock bits in the bitfield!
        0x01 = NumLock ON,  CapsLock OFF
        0x03 = NumLock ON,  CapsLock ON   ← explains log behavior during CAPS test

user_settings_config STRUCTURE (9 bytes, stored in emulated EEPROM):
  Byte 0: magic_num (0xBE = valid)
  Byte 1 bitfield: caps_lock, num_lock, scroll_lock, winlock_state,
                   kbd_lock, reset_factory, [reserved×2]
  Byte 2: kbd_dev_mode (0xFF = default/unset)
  Byte 3: bt_ch (BT channel, default=1)
  Byte 4: bt_used
  Byte 5: bt_last_connected (default=0xFF = none)
  Byte 6: reset_reason
  Byte 7: unused
